# GPU 여유와 4비트 소형 서버 추가 검증

[공개 비용·성능 표](https://d3q7tlfor72b22.cloudfront.net/costs.html) · [원본 측정](../research/rightsizing-followup/) · [이전 서빙 방식 비교](GPU_RIGHTSIZING.ko.md)

## 최종 비교 · 저렴한 GPU에서도 속도를 유지할 수 있었다

L4와 T4는 NVIDIA GPU 이름이고, `g6.xlarge`와 `g4dn.xlarge`는 GPU·CPU·시스템 메모리가 포함된 AWS EC2 서버 유형입니다. 이번에 실제 시험한 서버는 모두 서울 리전이며 **L4는 EC2 `g6.xlarge`, T4는 EC2 `g4dn.xlarge`**입니다. 현재 공유 데모는 `g6.xlarge`에서 실행합니다. 표의 월 비용은 해당 서버 한 대를 730시간 켜두는 인스턴스 가동비입니다.

**T4 + Qwen AWQ 4bit + vLLM은 이번 단독 요청 시험에서 L4 BF16과 비슷한 약 1초 응답과 같은 공통 성공 건수를 기록했습니다.** 동시 요청이 늘면 L4의 처리량과 지연이 더 좋았습니다. 두 구성 모두 같은 수정된 도구 스키마로 재측정한 결과입니다.

| AWS 인스턴스 · GPU · 구성 · 도구 스키마 v2 | 공통 / 추가 표현 | 첫 음성 중앙값 / p95 | 동시 요청 4개 p95 | p95 3초 이내 관측 처리량 | 월 인스턴스 가동비 · 730h |
| --- | ---: | ---: | ---: | ---: | ---: |
| EC2 `g6.xlarge` · NVIDIA L4 · BF16 · vLLM | 30/31 · 9/10 | 1.08 / 1.69초 | 2.70초 | 1.832건/초 | $722.41 |
| EC2 `g4dn.xlarge` · NVIDIA T4 · AWQ 4bit · vLLM | 30/31 · 9/10 | 1.01 / 1.58초 | 3.16초 | 1.255건/초 | $472.31 |

양쪽 모두 최종 부하 시험 96/96건을 통과했습니다. 추가 표현 중 차량 제어 9개는 모두 성공했고, 날씨 문항은 아래 설명한 과거 채점 기준 때문에 실패로 남겼습니다. 공통 명령의 남은 실패는 두 구성 모두 같은 음성 인식 오류였습니다. 작은 표본의 성공 건수 일치와 수십 밀리초 차이를 일반적인 품질 동등성·속도 우위로 확대하지 않습니다.

T4 한 대의 월 가동비는 약 35% 낮지만, 같은 p95 3초 조건에서 관측한 처리량도 낮습니다. 이 처리량으로 고정 가동비를 나눈 최대 활용 시의 GPU 비용은 1,000건당 L4 약 $0.150, T4 약 $0.143으로 차이가 작습니다. Polly·스토리지·네트워크 등은 제외한 계산이며 운영 용량 보장은 아닙니다. 저빈도에는 T4의 낮은 고정비가 유리할 수 있고, 높은 피크 부하에는 필요한 서버 수를 함께 계산해야 합니다. 현재 공유 데모는 L4를 유지합니다.

## 도구 스키마 수정과 공정한 재시험

처음 AWQ 시험은 29/31이었습니다. “온도를 1도 내려줘”에서 `temperature`의 `zone`이 빠졌는데, 기존 JSON 스키마가 모든 동작에 `type`만 필수로 요구해 잘못된 도구 인자를 허용했습니다. 실행기는 이를 거절해 차량 상태를 바꾸지 않았습니다.

[새 공통 스키마](../runtime/vehicle_plan_schema.py)는 동작마다 필수 인자를 요구합니다. 온도에는 `zone`과 `value`, 에어컨에는 불리언 `value`가 필요하며, 열선의 불필요한 `zone`이나 `undo`의 불필요한 `value`는 허용하지 않습니다. 기존 온도 범위 가드와 차량 실행기는 유지했습니다. 특정 답변을 주입하거나 실행 결과를 사후 정규화한 변경이 아닙니다.

L4와 T4에 같은 스키마를 적용하고 공통 31개·추가 표현 10개·부하 96건씩 다시 측정했습니다. AWQ의 온도 구역 누락은 해소돼 30/31이 됐고 L4도 30/31이었습니다. 원본 HF 입력과 AWQ vLLM의 실제 입력 토큰 657개는 전부 같았습니다. 수정 전 측정은 삭제하지 않고 별도 디렉터리와 공개 페이지의 접힌 표에 보존했습니다. `PLANNER_SCHEMA_VERSION=legacy-generic-v1`은 이전 형식을 재현하는 옵션이며 기본값은 `typed-actions-v2`입니다.

AWQ의 빈 컴파일 캐시에서 첫 정상 추론까지는 약 560초가 걸렸습니다. 가중치는 이미 캐시된 상태였고, 프로파일러로 Qwen GDN 커널의 컴파일·튜닝을 확인했습니다. 예열 후 응답 속도와 별도인 첫 초기화 비용입니다. 캐시를 보존한 재시작 시간과 장시간 안정성은 아직 측정하지 않았습니다. 즉시 증설 가능한 서버가 되려면 이 준비 과정까지 검증해야 합니다.

## 이미 모델을 함께 쓰면 더 올릴 수 없을까?

그렇지는 않습니다. 같은 L4에 Whisper와 Qwen이 이미 올라가 있어도 메모리에 다른 모델을 적재할 여유가 있을 수 있습니다. 요청이 없는 시간에는 GPU 연산도 대부분 쉬고 있습니다. Docker는 실행 환경을 나누는 수단이며, 기본 GPU 공유 설정만으로 각 컨테이너의 연산량이나 지연을 보장하지 않습니다.

이번에는 **같은 Qwen 모델 복제**와 **다른 단계인 Whisper 복제**를 구분했습니다. 이전 Phi HF 판단 모델 복제는 처리량을 개선하지 못했지만, 이번에는 직렬 음성 인식의 대기를 줄이려고 Whisper를 하나 더 적재했습니다. 두 ASR 워커의 요청 카운터는 각각 145건, 144건으로 실제 분산을 확인했습니다. 추가 워커는 systemd의 별도 프로세스로 시험했습니다. GPU 연산·메모리의 하드 격리를 구성한 시험은 아닙니다.

## 같은 L4에서 Whisper 1개와 2개 비교

공통 조건은 서울 `g6.xlarge`의 L4 한 장, Qwen3.5-4B BF16 한 벌을 적재한 vLLM 0.32.0, 동일 Whisper turbo 체크포인트, 서울 Polly입니다. 각 부하 단계는 한국어 녹음 명령 6종을 반복한 48건입니다. 모든 요청은 새 차량 세션에서 상태 변경과 실제 음성 수신을 함께 검사했습니다. 각 구성 240/240건을 통과했습니다.

| 동시 요청 | Whisper 1개 처리량 | Whisper 2개 처리량 | 첫 음성 p95 · 1개 | 첫 음성 p95 · 2개 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 0.843건/초 | 0.812건/초 | 1.52초 | 1.53초 |
| 4 | 1.924건/초 | 2.048건/초 | 2.53초 | 2.43초 |
| 8 | 2.583건/초 | 2.991건/초 | 3.99초 | 3.53초 |
| 16 | 2.561건/초 | 3.586건/초 | 6.70초 | 5.82초 |
| 32 | 2.547건/초 | 3.620건/초 | 12.67초 | 9.71초 |

높은 부하 처리량은 약 42% 개선됐습니다. 다만 그 수치는 **p95 약 9.71초를 수반한 최대 관측값**입니다. p95 3초 이내를 유지한 관측 처리량은 1.924→2.048건/초로 약 6% 개선됐습니다. 항상 듣는 차량 수, 장시간 운영 용량, 운영 SLA로 환산하지 않습니다.

두 ASR 구성도 공통 명령 30/31, 추가 표현 9/10을 기록했습니다. 공통 실패는 “길 안내 종료”를 Whisper가 “기회 안내 종료”로 인식한 경우였습니다. 추가 표현의 `holdout-weather`는 과거의 “날씨 기능을 거절해야 성공” 기준이 남아 있어 실패로 집계됐지만, 현재 앱은 실제 날씨를 조회해 답했습니다. 원점수는 유지하고 이 기준 불일치를 공개합니다. 추가 표현 중 차량 제어 9개는 모두 통과했습니다. 이 점수는 앱 전체 결과이며 모델 자체의 순수 언어 능력 점수가 아닙니다.

## 메모리가 남아도 연산 여유와 같지는 않다

약 1초 간격으로 전체 인스턴스 자원을 측정했습니다. 시스템 RAM은 Linux `MemAvailable`, GPU 메모리는 다른 프로세스와 vLLM 예약 캐시를 포함합니다.

| 구성 · 동시 요청 32개 | GPU busy 평균 | CPU 평균 | GPU 잔여 최소 | 시스템 RAM 여유 최소 |
| --- | ---: | ---: | ---: | ---: |
| Whisper 1개 | 100% | 약 32% | 약 3.34GiB | 약 8.83GiB |
| Whisper 2개 | 100% | 약 54% | 약 1.16GiB | 약 7.57GiB |

GPU busy 100%는 샘플 구간 동안 GPU 작업이 있었다는 뜻이며, 모든 연산 유닛·메모리 대역폭을 최대치로 사용했다는 증거는 아닙니다. 실제로 ASR을 추가하자 처리량이 더 늘었습니다. 기존의 약 2.5건/초 한계에는 ASR 직렬 처리와 파이프라인 스케줄링도 영향을 주었습니다. 정확한 하드웨어 병목은 별도 프로파일링하지 않았습니다.

가벼운 CPU 서비스는 남는 시스템 RAM에 함께 배치할 수 있습니다. 추가 GPU 모델도 적재할 수 있으나, 피크 부하에서의 음성 지연과 메모리 여유를 다시 확인해야 합니다. vLLM의 `--gpu-memory-utilization 0.75`는 해당 엔진의 메모리 예산 설정이며 GPU 연산의 75%를 격리한다는 뜻이 아닙니다.

## 재현과 측정 범위

- `WHISPER_URLS=http://127.0.0.1:9105,http://127.0.0.1:9106`을 평가 API에 지정하면 독립 ASR 워커로 최소 활성 요청 수에 따라 분산합니다. 기본 설정은 단일 워커입니다.
- [부하 스크립트](../scripts/serving-load-benchmark.mjs)는 `BENCH_CONCURRENCY`, `BENCH_REQUESTS`, `BENCH_WARMUP_REQUESTS`를 받습니다. 두 ASR 시험은 네 번 예열해 양쪽 워커 모두 실제 추론을 마쳤습니다.
- [자원 수집기](../runtime/resource_monitor.py)는 GPU 호스트에서 실행합니다. 부하 단계의 시작·종료 시각에 맞춰 자원 샘플을 집계합니다.
- [요약 스크립트](../scripts/summarize-rightsizing-followup.mjs)가 원본 JSON을 공개 페이지용 보고서로 변환합니다.
- 공개 API의 분당 요청 제한은 유지했습니다. 초기 공개 백엔드 부하 시도가 429 제한에 걸려, 이후에는 기존 모델을 공유하는 별도 loopback 평가 API로 측정했습니다. 제한에 걸린 시도는 성능 수치에서 제외했습니다.
- 짧은 반복 명령, 공통 프롬프트와 prefix cache의 효과를 포함합니다. 긴 대화·다양한 입력·장시간 운영·실차 마이크 시험은 별도입니다.

## 더 저렴한 T4에서 4비트 모델 검증

서울 `g4dn.xlarge`의 T4 16GB에 같은 Qwen 체크포인트를 NF4로 적재했습니다. T4는 네이티브 BF16을 지원하지 않아 4비트 가중치의 계산과 나머지 모듈에는 FP16을 사용합니다. 부팅 후 패키지 업데이트와 모델 적재를 마치고 실제 추론을 예열한 뒤 측정했습니다.

| 구성 | 공통 명령 | 추가 표현 | 공통 명령 첫 음성 중앙값 | 공통 명령 첫 음성 p95 | 월 인스턴스 가동비 · 730h |
| --- | ---: | ---: | ---: | ---: | ---: |
| 기존 EC2 `g6.xlarge` · L4 · Qwen BF16 · vLLM | 30/31 | 이번 재시험 없음 | 1.21초 | 2.28초 | $722.41 |
| EC2 `g4dn.xlarge` · T4 · Qwen NF4 · HF / FP16 계산 | 30/31 | 8/10 | 2.88초 | 3.93초 | $472.31 |

T4의 추가 표현은 엄격한 원점수로 8/10입니다. 날씨 문항의 과거 거절 기준 외에, 열선 3단 명령에 불필요한 `zone: driver` 필드가 추가돼 정확한 명령 형식 비교에서 실패했습니다. 열선 상태 자체는 정상 변경됐고, 차량 제어 9개의 최종 상태는 모두 맞았습니다. 상태 성공과 명령 형식 성공을 구분해 원점수를 유지합니다.

T4의 판단 모델 CUDA 적재는 약 3.08GiB이고 346개 Linear4bit 레이어를 확인했습니다. 이 설정은 원래 체크포인트를 로드하면서 양자화한 bitsandbytes NF4입니다. 정확도는 이 작은 공통 시험에서 유지됐지만, 인스턴스 비용 약 35% 절감에 응답 지연 증가가 따릅니다. 단일 요청의 공통 시험 p95부터 3초 비교 기준을 넘었습니다. 이 결과는 **T4 + HF NF4/FP16의 조합**에 해당하며, 모든 4비트 추론 엔진이 느리다는 결론은 아닙니다.

| T4 NF4 · 동시 요청 | 성공 | 성공 처리량 | 첫 음성 p95 | 판단 대기 p95 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 24/24 | 0.284건/초 | 4.71초 | 0초 |
| 2 | 24/24 | 0.325건/초 | 7.31초 | 2.97초 |
| 4 | 24/24 | 0.317건/초 | 13.69초 | 10.16초 |
| 8 | 24/24 | 0.324건/초 | 25.56초 | 21.76초 |

T4 부하 시험 96건도 모두 상태 변경과 음성 수신에 성공했습니다. 동시 요청 8개의 GPU busy 평균은 약 48%, GPU 잔여 최소는 약 9.52GiB, CPU 평균은 약 30%였습니다. 따라서 약 0.32건/초를 T4 하드웨어 자체의 최대 성능이라고 해석하지 않습니다. 이 구성은 직렬 HF 판단 워커를 사용하므로 동시 요청이 GPU 전체 활용으로 이어지지 않았습니다. **메모리가 남으면서 응답은 느릴 수 있습니다.** 다른 엔진이나 T4의 복제본 구성이 이 여유를 얼마나 활용하는지는 별도 실측 사항입니다.

p95 5초를 허용하는 저빈도 서비스라면 T4 NF4도 비용 절감 후보입니다. 이번 반복 부하에서 그 기준을 만족한 관측 처리량은 T4 0.284건/초, 기존 L4 2.583건/초였습니다. 월 서버 한 대의 가격 절감과 같은 지연 조건에서의 처리량을 함께 비교해야 합니다.

현재 설치한 vLLM 0.32.0 이미지에는 bitsandbytes 백엔드가 없습니다. vLLM 4비트 비교에는 별도 AWQ 체크포인트가 필요하며, [커뮤니티 AWQ 체크포인트와 revision](../research/rightsizing-followup/awq-checkpoint.json)을 고정했습니다. AWQ와 NF4는 다른 양자화 방식이므로 품질과 호환성을 각각 검증해야 합니다. 원본 모델 제작자의 공식 AWQ 배포라는 뜻은 아닙니다.
